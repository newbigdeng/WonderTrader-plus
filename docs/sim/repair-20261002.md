# 本地模拟盘修复：成交字段、退出顺序与状态恢复

9 月 30 日实验能开平仓，却暴露累计量为负、日期为零、退出崩溃和快照滞后。10 月 2 日基于 `c7c5619` 加工作区补丁修复，14 个集成场景与 54 项单元测试通过。本文把根因、改法与验证放在一起；本次整理没有新增源码修复。

## 1. 累计成交量为什么会变成负数

一手单显示 traded=-1，三手单显示 -3，但实际成交流水数量为正。沿 `TraderMocker.cpp` 的分笔撮合更新发现，同一笔成交量被用于减少累计已成交字段。

剩余量应该减，累计已成交量应该加。修复后每次成交 q 同时满足：累计成交增加 q，剩余量减少 q，总委托量守恒。三手订单分三次各成交一手，最终累计字段为 3，开平各一张订单、各三条成交。

这次验证同时看委托终态与成交流水。只看持仓归零，可能漏掉回报字段错误。

修改前：剩余量与累计成交量都减去本次成交量。

```cpp
ordInfo->setVolLeft(ordInfo->getVolLeft() - curVol);

```

```cpp
ordInfo->setVolLeft(ordInfo->getVolLeft() - curVol);
ordInfo->setVolTraded(ordInfo->getVolTraded() + curVol);
```

假设委托3手、每次成交1手，正确状态依次是`剩余/累计 = 2/1 → 1/2 → 0/3`。买卖方向由其他字段表达；累计成交量不是卖单的有符号净量，不能用负数表达卖出，也不能事后取绝对值来掩盖错误。

## 2. 日期与交易日分别表示什么

旧委托和成交日期没有赋值，输出为 0。修复从同一次本地时钟采样取得自然日和毫秒时间，避免跨午夜分别采样造成日期、时间不一致。

自然日是这件事在本地何时发生，交易日是所属结算周期；夜盘可能属于下一交易日。测试专门设置二者不同，核对字段语义。真实柜台夜盘归属仍需接入后验证。

首轮测试还遇到容器缺 IANA 时区文件，改用 POSIX 时区后重测。这属于测试环境处理，历史失败保留，没有记为产品日期修复的新缺陷。

<summary>展开：委托日期和成交日期修改前后代码</summary>


旧版创建成交时也只有时间戳赋值：

```cpp

```

修复后：

```cpp
uint32_t tradeDate, tradeTime;
TimeUtils::getDateTime(tradeDate, tradeTime);
trade->setTradeDate(tradeDate);
trade->setTradeTime(TimeUtils::makeTime(tradeDate, tradeTime));
```

不能分别取一次日期、再取一次时间，否则在午夜边界可能组成不一致的一对值。这里修复的是本地模拟接口的“发生自然日”字段；交易日仍表示结算归属。例如夜盘自然日为10月14日、交易日为10月15日，两者不同可以是正确结果，不能无条件拿交易日填入上述日期字段。

</details>

## 3. 为什么收到 SIGINT 后会崩溃

问题不是一个 stop 标志：时钟、网络、writer、广播和撮合线程仍可能回调已经销毁的对象。旧路径既可能因线程尚可 join 而 terminate，也可能在对象析构后发生纯虚调用。

沿引用方向建立停止顺序：先封外部输入，唤醒并停止工作线程，等回调和任务结束，再释放被调用对象。主线程执行有序关闭，模块持有自己的线程并 join；不能用 sleep 代替完成确认。

修复覆盖 WtRunner、QuoteFactory 及 parser、engine/ticker、writer、caster、监控与交易接口。等待期间仍要允许已接纳任务完成，避免下游先停导致上游永远无法排空。

以下对照来自2026-10-08已核对并留存的修复说明：旧代码基于`c7c5619`，新代码为10月2日本地回归的`sim-fix-20261002`源码。此次补回代码只完善文档，**没有重新执行这些历史测试**；也不能把C++ WtRunner的关闭结果套用到当前wtpy入口。

<details class="source" markdown="1">
<summary>展开：CTA引擎和时钟线程修改前后代码</summary>

**基线：析构时直接 delete 仍可能运行的 ticker**

```cpp
WtCtaEngine::~WtCtaEngine()
{
	if (_tm_ticker)
	{
		delete _tm_ticker;
		_tm_ticker = NULL;
	}

{

	if (_thrd)

}
```

这里的关键不是 `delete` 本身，而是析构函数没有先调用 `stop()`；同时 ticker 的析构函数是空的，线程对象仍处于可 join 状态时被销毁会触发 `std::terminate`。

**修复版：把停止、等待和状态落盘放进显式关闭路径**

```cpp
WtCtaEngine::~WtCtaEngine()
{
	stop();
	if (_tm_ticker)
	{
		delete _tm_ticker;
		_tm_ticker = NULL;
	}

	if (_cfg)
		_cfg->release();
}

void WtCtaEngine::stop()
{
	if (_terminated)
		return;
	if (_tm_ticker)
		_tm_ticker->stop();
	if (_pool)
		_pool->wait();
	WtEngine::stop();
	if (_tm_ticker)
	{
		for (auto& item : _ctx_map)
		{
			auto ctx = dynamic_cast<CtaStraBaseCtx*>(item.second.get());
			if (ctx)
				ctx->flush_state();
		}
		save_datas();
	}
}

void WtCtaRtTicker::stop()
{
	_stopped = true;
	if (_thrd && _thrd->joinable())
		_thrd->join();
	_thrd.reset();
}
```

修复版先让行情时钟退出，再等待策略任务池，随后保存策略状态；`joinable()` 和 `reset()` 让重复关闭不会再次 join 同一线程。HFT、SEL 也补上了同一公共 stop 语义。

</details>

### 跨线程对象为什么还会访问已释放内存

`WTSPoolObject` 的旧线程局部池在生产线程退出时释放存储，而其他线程可能仍持有对象。引用计数保住了对象的逻辑身份，却没保住承载它的池内存。

改为共享池状态，使池的存活覆盖所有借出的对象；线程局部入口结束不再提前释放仍被引用的底层存储。由于对象布局与池契约改变，相关模块必须成套重新编译。

独立 ASan 对照中旧版退出码 1，新版 0，定位到的 use-after-free 消失。这是对应对象池场景的证据，完整应用所有路径仍需独立验收。

<details class="source" markdown="1">
<summary>展开：线程局部对象池与共享池修改前后代码</summary>

对象池问题的最小代码对照如下。它解释了为什么“线程已经退出，但对象仍有引用”会成为真正的 use-after-free，而不是普通的析构顺序偏好。

**基线：对象保存分配线程 TLS 的裸指针**（`src/Includes/WTSObject.hpp`）

```cpp
thread_local static MyPool		pool;
thread_local static SpinMutex	mtx;

mtx.lock();
T* ret = pool.construct();
mtx.unlock();
ret->_pool = &pool;
ret->_mutex = &mtx;
return ret;

// 最后一个引用释放时仍使用上面的 TLS 地址
_mutex->lock();
_pool->destroy((T*)this);
_mutex->unlock();
```

分配线程的 TLS 析构后，`_pool` 和 `_mutex` 指向的对象已经不存在；另一个线程最后释放对象时就会解引用悬空地址。

**修复版：对象与共享 PoolState 一起延长池的寿命**

```cpp
struct PoolState
{
	MyPool pool;
	SpinMutex mutex;
};
std::shared_ptr<PoolState> _pool;

thread_local static std::shared_ptr<PoolState> pool(new PoolState);
SpinLock lock(pool->mutex);
T* ret = pool->pool.construct();
if (ret)
	ret->_pool = pool;
return ret;

if (m_uRefs.fetch_sub(1) == 1)
{
	auto pool = _pool;
	SpinLock lock(pool->mutex);
	pool->pool.destroy(static_cast<T*>(this));
}
```

最后一次 `release()` 先复制一个局部 `shared_ptr`，确保池和锁在对象销毁完成前仍然存在，再在锁内归还对象。

</details>

## 4. 最终状态应该在什么时候保存

策略理论目标和模拟通道实际持仓是两本账。目标 3、只成交 1 手时，前者仍是 3，后者是 1；保存时强行写成一样会丢掉剩余执行责任。

正常停止先等时钟和引擎任务结束，再保存策略最终状态；模拟器停止撮合和 I/O 后保存实际通道持仓。重启保持策略、执行器、通道 ID 及状态目录，重新计算目标与实际差额。

原运行中的 `save_data` 顺序仍可能早于资金汇总或信号删除。补最终保存修复的是正常关闭快照，运行中资金快照滞后（SIM-04）仍待修复。

<details class="source" markdown="1">
<summary>展开：TraderMocker正常释放与持仓保存修改前后代码</summary>

**基线：TraderMocker 只停线程，没有在正常释放路径做最后一次持仓保存**

```cpp
void TraderMocker::release()
{
	if (_terminated)
		return;

	_terminated = true;
	if (_thrd_match)
		_thrd_match->join();
	if (_thrd_worker)
	{
		_io_service.stop();
		_thrd_worker->join();
	}
}
```

这段代码让撮合和 API 线程停止，却没有调用 `save_positions()`。因此最后一笔成交发生在上次周期性保存之后时，进程退出后 `positions.json` 仍是旧快照；下次启动按旧实际持仓计算缺口，就可能重复开仓。它也没有把线程指针复位，重复释放的安全性不足。

**修复版：线程完全退出后保存一次，且只对已建立 worker 的实例保存**

```cpp
void TraderMocker::release()
{
	const bool saveCheckpoint = (_thrd_worker != NULL);
	_terminated = true;
	if (_thrd_match && _thrd_match->joinable())
		_thrd_match->join();
	_thrd_match.reset();
	if (_thrd_worker && _thrd_worker->joinable())
	{
		_io_service.post([this]{ _io_service.stop(); });
		_thrd_worker->join();
	}
	else
		_io_service.stop();
	_thrd_worker.reset();
	if (_b_socket)
	{
		boost::system::error_code ec;
		_b_socket->close(ec);
		delete _b_socket;
		_b_socket = NULL;
	}
	if (saveCheckpoint && !_pos_file.empty())
		save_positions();
}

void TraderMocker::disconnect()
{
	release();
}
```

`saveCheckpoint` 是一个有意的边界：已连接并启动 worker 的模拟器，在线程全部结束后写最终实际持仓；只调用 `init()`、从未连接的对象不会用空内存状态覆盖已有 `positions.json`。这个保存的是通道实际成交仓位，不是策略目标，也不保存旧的在途委托队列。

策略账本的最终保存由 CTA engine 的 `stop()` 调用 `ctx->flush_state()` 和 `save_datas()` 完成，交易账本则由上面的 `save_positions()` 完成；两者都必须在线程停止后执行。它们是两个文件、两个职责，本轮没有实现跨文件的原子事务。

</details>

## 5. 用哪些场景证明修改有效

| 场景 | 结果与验证点 |
|---|---|
| 基线一手开平 | 两张终态订单、两条成交，最终空仓，字段正确 |
| 三手分笔 | 两张终态订单、六条一手成交，累计成交字段各为 3 |
| SIGINT、SIGTERM、空闲退出 | 正常停止返回 0，线程可被唤醒并完成 |
| 突发 200 条后关闭 | 存储原生块读出全部 200 条 |
| 留一手、重启保持、再次平仓 | 重启没有新增开仓，最后只新增一次平仓 |
| 目标三手但一手时退出 | 理论目标 3 与通道持仓 1 分别保存；重启只补两手 |
| HFT/SEL 空闲退出 | 公共停止接口的对应兼容场景通过 |
| 自然日与交易日不同 | 日期非零，与同次时间戳采样一致 |

共 14 场景、28 次进程关闭返回 0，没有用强杀换取退出成功。54 项单元测试由 48 项 CTA 模型、3 项费用和3项池生命周期测试组成。另有独立初始化释放检查通过。

订单 CSV 只记录终态，三手单仅成交一手时可能尚无订单行，但已有成交行；数量验收必须结合回报和流水。
