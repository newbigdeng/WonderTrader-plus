核对日期：2026-10-13。本文说明当前源码为什么这样拆分，以及从研究框架走向可长期运行的交易工具还需要补什么。标为“已有”的内容可在源码找到；标为“建议”的内容是后续设计，不代表已经实现或验收。本轮只核对第一套 simnow-03 配置和依赖，没有启动 CTP、发送订单或运行性能测试。源码依据是 VM 的 c7c5619 加此前工作区修复、隔离 CTP 6.7.13 适配和配套 wtpy；Windows 学习版注释与 VM 行号可能不同，以函数名定位。

## 1．把 WT 看成几份职责明确的账和事件流

交易程序不能只有“读价格→算买卖→下单”三行逻辑。它还要回答：行情是否新鲜？买卖规则是否正确？柜台是否已准备好？订单有没有成交？重启之后该相信哪个持仓？WT 的分层是在处理这些不同问题。

```text
外部行情          行情中台             策略/组合               执行层             外部交易
CTP MD → ParserCTP → Writer/存储 → UDP/SHM → Engine/Strategy → Executer → TraderAdapter → TraderCTP → CTP TD
                                      ↑        ↓                  ↑                   ↑
                              Reader 读历史/实时     目标仓位       订单状态/实际持仓 ← 柜台回报
```

此处 CTP MD 是行情接口，CTP TD 是交易接口。LoaderRunner 只是合约元数据查询工具，不在持续行情或订单的主链路内。Python 策略接入之后，改变策略入口与事件回调，后面的行情存储、执行、交易适配仍由 C++ 完成。

可以按职责认识五层：

| 层 | 它决定什么 | 为什么独立 |
|---|---|---|
| 行情接入 | 外部数据怎样转成 WT 的 Tick | 不同厂商字段、日期语义、无效价格和订阅方式不同 |
| 行情中台 | 数据怎样保存、形成 K 线、供多个消费者使用 | 多个策略可复用一份行情，不必重复连接和写盘 |
| 引擎与策略 | 什么时刻计算、最终希望持有多少仓位 | 策略规则与柜台报单细节分离，方便复用和组合 |
| 执行层 | 怎样把目标逐步变成实际持仓 | 信号正确不意味着立刻按理想价格成交，需要处理拆单、挂单和撤单 |
| 柜台适配 | 委托如何编码、回报如何转换 | 通道认证、开平标志、私有流、柜台查询与协议各不相同 |

源码入口分别是 `src/ParserCTP/ParserCTP.cpp`、`src/QuoteFactory/main.cpp`、`src/WtCore/WtCtaEngine.cpp`、`src/WtCore/WtLocalExecuter.cpp` / `src/WtExeFact/WtMinImpactExeUnit.cpp`、`src/WtCore/TraderAdapter.cpp` / `src/TraderCTP/TraderCTP.cpp`。

**分层使替换组件和定位问题更清楚；可靠性还取决于每层的状态与错误处理。** 比如更换 CTP SDK 主要影响 ParserCTP、TraderCTP 和 CTPLoader；策略不会因此重写。但接口布局、动态库符号和依赖仍需一致，前置登录成功也不能替代订单闭环验收。

## 2．行情中台把“处理速度”和“数据留存”组织在一起

### 已有设计

中台把柜台 Tick 转成统一结构，先更新最新快照、当日 Tick、分钟 K 线，再调用注册的广播器。关键处理顺序见 `src/WtDataStorage/WtDataWriter.cpp` 的 `procTick`（VM 约 399 行）：

```cpp
// 核心摘录，ct / commInfo 已由前面取得
if (!_sink->canSessionReceive(commInfo->getSession()))
    break;
if (!updateCache(ct, curTick, procFlag))
    break;
if (!_disable_tick)
    pipeToTicks(ct, curTick);
pipeToKlines(ct, curTick);
_sink->broadcastTick(curTick);
```

这种顺序让策略事件与中台存储属于同一数据处理链。实时文件使用 mmap，把磁盘文件映射到进程地址空间；Reader 可以读取同一文件，而不需要每次向中台请求完整历史。历史文件压缩为 `.dsb`，供后续数据查询和回放使用。

但 `mmap` 不是“写内存后每条都已安全写盘”，UDP 也不是“每条必达”。本版本 SHM 队列是容量 8192 的环形映射文件，读写索引使用 `volatile`；未见严格的原子发布协议和消费滞后的可靠补齐。它们是当前实现方式，需要独立检查数据可靠性，不能拿“C++”“共享内存”“无锁”几个词当作性能或安全证明。

### 对业务的影响

一份行情服务可以同时支持策略、行情观察和数据积累，减少每个进程独立订阅与转换的重复工作。代价是中台成为共同依赖：中台没有收到或没有接受的 Tick，正常链路下也不会继续广播。

排查因此应沿链路逐段计数：柜台回调数、中台接受数、保存数、广播数、Runner 接收数、策略事件数。只看“文件存在”或“进程存活”不能证明数据持续可用。

### 建议的产品化补充

把数据时间和状态变成可见指标：最后收到的交易日、自然日、行情时间、本机接收时间、最后策略事件时间、队列积压和异常计数。为每个目标合约定义缺数据与过期阈值，触发时停止新开仓，并保留处理已有订单与退出仓位所需的逻辑。

UDP 如果继续使用，应接受其有丢包风险的性质，并设计检测和必要的补齐；不能把订阅端口的“最新快照回包”误称为历史重传。是否改用 SHM、是否增加序号、怎样处理环形覆盖，应该由实测吞吐和可靠性需求决定，先明确需求再改代码。

## 3．CTA 为什么用目标仓位，为什么要区分理论仓与实仓

### 已有设计

CTA 表达的是“我希望持有多少”，例如 `stra_set_position("SHFE.rb.2701", 1)` 表示目标净多 1 手。它不是每调用一次就买 1 手。上下文将目标保存为信号，并按后续行情/调度更新理论持仓。

源码 `src/WtCore/CtaStraBaseCtx.cpp::stra_set_position`（VM 约 1360 行）核心是：

```cpp
_engine->sub_tick(id(), stdCode);
if (decimal::eq(limitprice, 0.0) && decimal::eq(stopprice, 0.0))
    append_signal(stdCode, qty, userTag, _is_in_schedule ? 0 : 1);
// 带条件价时则登记条件目标，等待条件满足
```

`on_tick` / `on_schedule` 处理信号，`do_set_position` 维护策略理论账。`WtCtaEngine` 汇总策略目标、处理主力映射与过滤、通过 `WtExecuterMgr` 按路由交给执行器。

执行器查 TraderAdapter 的真实持仓与未完成量，结合目标决定等待、撤单或继续下单。订单没完成时不能简单重复提交“目标减持仓”的数量，否则会累计出超量挂单。`WtMinImpactExeUnit::do_calc` 就在处理这些状态。

### 为什么保留两本账

理论账帮助分析策略本身的信号和理论贡献；柜台账说明账户实际持有与实际成交。当前没有把净额后的每一笔真实成交自动、唯一地分配回各 CTA 策略的通用归因链，理论收益不能直接充当逐策略实际收益。多策略交易同一真实合约且进入同一个执行目标组时，策略 A 想多 1、策略 B 想空 1，净目标可能为 0；不必为了两个策略的理论变化在柜台来回成交。具体净额按合约和执行路由聚合；不同路由、缩放与过滤会改变最终目标，不能说所有策略无条件全局合并。

`WtCtaEngine::on_schedule` 枚举策略仓位并提交缓存；`WtExecuterMgr::add_target_to_cache` 的实际累加按执行器分组：

```cpp
// src/WtCore/WtExecMgr.cpp::add_target_to_cache
TargetsMap& targets = _all_cached_targets[execid];
double& vol = targets[stdCode];
vol += targetPos;
```

定时调度是全量收集；条件目标等即时变化还可经`handle_pos_change`走增量路径。两条路径都必须与路由和当前执行状态一起理解。

这种设计也带来一个必须理解的差异：理论 `trades.csv` 可能已有记录，柜台却还没成交，甚至订单被拒绝。普通 Python CTA 没有柜台 `on_order/on_trade` 钩子，真实订单回报主要进入 TraderAdapter→执行器及其执行单元。

```text
策略目标 / 理论仓位 → 组合目标 → 执行器目标
                                 ↓
                      实际持仓 + 未完成订单 → 下一步委托
                                 ↑
                        订单回报与实际成交
```

因此盈利分析至少应区分：信号本身、理论成交、实际成交、手续费和执行偏差。不能只展示漂亮的理论收益就证明实盘可盈利。

### 建议的产品化补充

建立每日及重启后的对账：策略理论仓、组合目标、执行器目标、实际多空今昨仓、未完成订单、柜台权益与可用资金。对不一致给出具体原因：尚未成交、部分成交、被过滤、被风控缩量、柜台拒单、目标已变化或恢复状态不一致。

交易通道 ready 后仍应检查有效资金、行情新鲜度和账户已有仓位；不能把“模块加载成功”当作放行条件。`strict_sync` 会清理未纳入目标管理的账户持仓，应明确选择和展示，不能在新实验中默认把旧账户的仓位当作垃圾数据。

### 风控为什么需要分层

策略知道信号和止损，组合知道多个策略的总体风险，执行器知道挂单与成交进度，柜台知道实际资金和交易约束。信息不同，控制点也不同；把所有风险都塞进策略，会让不同策略重复使用同一笔可用资金。

| 控制位置 | 已有能力与作用 | 当前 simnow-03 |
|---|---|---|
| 策略 | 手数、单笔估算、日亏、持有时间等交易意图约束 | 已写入 Python；离线场景通过，依赖理论账 |
| 组合 | SimpleRiskMon 可按组合损益缩放目标 | 当前关闭，不能写成已启用 |
| 执行/通道 | 分笔、价格、超时撤单；下单/撤单次数限制 | exec03 一手，通道流控开启；在线闭环待验收 |
| 柜台 | 实际保证金、冻结资金、可用资金和最终报单检查 | 来自 CTP；本轮未登录查询 |

产品层还需账户集中预算和预留：两个策略各看到 available=1万元，不代表它们可以各花1万元。应在唯一的账户执行入口预留预算，部分成交、拒单和撤单后再按确定规则更新。当前 WT 有保证金字段和柜台资金查询，本地 TraderMocker 与 CTA 回测没有因此自动具备完整的期货冻结/释放账本，详见[08 保证金与因子数据库](08_保证金风控与因子数据库.md)。这是能力边界和建设建议，本轮未实现新资金引擎。

## 4．进程、事件和插件：哪些边界是真隔离

### 进程边界

QuoteFactory 与 Runner 通常是两个进程，通过 UDP / SHM 传行情；这样数据积累与策略计算可以分别启动、停止，多个引擎也能复用中台。监控又是独立进程，读取生成文件、消费通知并提供页面。

ParserCTP、TraderCTP、数据 Reader、执行器工厂则通常是**进程内动态库**。插件替换灵活，但插件崩溃仍可能让宿主进程退出，不能把插件边界当成故障隔离边界。普通 wtpy 策略也通过回调在加载原生库的 Python 进程内运行，不是自动隔离的独立服务。

### 事件边界

柜台连接、认证、登录、查询、订单状态和成交通过异步回调推进。CTP 请求返回 0 表示 API 接受调用，业务结果要看后续回报；若提交成功后回报错误，系统必须按回报修正状态。

`src/WtCore/TraderAdapter.cpp` 的实际登录推进关系是：

```text
run → registerSpi → connect
→ handleEvent(WTE_Connect) → login
→ onLoginResult 成功 → queryPositions
→ onRspPosition → queryOrders
→ onRspOrders → queryTrades
→ onRspTrades → queryAccount
→ onRspAccount → 通道 ready
```

策略 Tick / 分钟调度、柜台回调、Writer 工作线程和组合风控线程存在不同线程上下文；源码使用锁、任务队列和可选线程池组织访问。不能因为有事件回调就认为所有代码都在一个线程，更不能随意把 Python 策略中的网络请求或数据库扫描塞进行情回调。

### 插件边界

`IParserApi`、`ITraderApi`、`ExecuteUnit` 定义约定的业务接口。宿主根据配置加载 `.so` / `.dll`，查工厂入口，创建对象并注册 SPI。

```cpp
// src/WtCore/TraderAdapter.cpp::init，摘录
FuncCreateTrader pFunCreateTrader =
    (FuncCreateTrader)DLLHelper::get_symbol(hInst, "createTrader");
_trader_api = pFunCreateTrader();
// init(params) 后，run() 注册 SPI 并连接
```

插件返回的是 C++ 接口对象，因此编译器、平台位数、接口头文件和依赖需要匹配。这不是跨语言、跨任意版本都能直接互换的网络协议。新 CTP SDK 增加 API 创建函数参数后，Linux 导出符号也变化，恰好说明“文件名一样”不能代表二进制契约没变。

已有设计适合以接口替换外部组件；产品化仍建议固定一套运行包的版本、平台与配置契约，并在启动前检查必需入口和目录。无需为小改动堆叠哈希或重建全套测试，应把验证集中到实际改变的契约。

## 5．C++ / Python 桥接的业务取舍

### 已有设计

Python `WtEngine` / `WtWrapper` 通过 ctypes 加载 WtPorter；C++ `ExpCtaContext` 继承 CTA 共同上下文，把策略事件传给 Python，再接收 Python 的目标仓位调用。

```cpp
// src/WtPorter/ExpCtaContext.cpp
void ExpCtaContext::on_calculate(uint32_t curDate, uint32_t curTime)
{
    getRunner().ctx_on_calc(_context_id, curDate, curTime, ET_CTA);
}
```

```python
# wtpy/wrapper/WtWrapper.py，摘录
def on_stra_calc(self, id, curDate, curTime):
    ctx = self._engine.get_context(id)
    if ctx is not None:
        ctx.on_calculate()
```

这种分工让研究代码可以使用 Python 的数组、分析和模型工具，同时复用 C++ 的行情、持仓、执行器和柜台链路。C++ 策略工厂更适合希望统一原生部署、减少语言边界的场景；Python 更便于快速表达和检查策略。

取舍不是“C++ 一定更快、Python 一定不行”。真正需要测量的是目标策略的计算耗时、事件排队、回调次数、跨边界传输的数据量与下单链路时间。重模型若每个 Tick 重算，可能影响事件处理；分钟策略可能根本不受此瓶颈限制。

### 建议的产品化补充

把重计算和实时决策的边界说清：启动前加载模型与历史，运行中只计算必要增量；需要异步计算时，结果必须带数据时刻与版本，并在使用前检查是否过期。先根据测量决定是否拆进程或改 C++，不要为了“性能”复制一套交易引擎。

Python 入口的退出与恢复必须单独验收。当前 `WtRtRunner::release()` 只停止日志，没有显式按 C++ WtRunner 的顺序停止 parser、engine、trader。已有 C++ 退出修复不能直接套成 Python 退出也已修复；需要检查回调停止、线程回收和最终状态落地后，再放行带仓运行。

## 6．回测、模拟与实盘：复用策略接口，逐层验证语义

WT 分开组织不同引擎，也是因为业务的调度方式不同：CTA 适合少标的、计算较快的事件/时间驱动策略；SEL 更适合多标的和较重的定时重算；HFT 给策略更直接的行情、委托和成交事件。当前 simnow-03 选择 CTA，是因为一分钟单品种信号适合目标仓位表达；若策略依赖逐笔挂撤单和队列位置，应先判断 CTA 接口是否足够，不能仅把计算周期调短就当成高频系统。

回测用 `HisDataReplayer` 推进历史事件时钟，`CtaMocker` 维护理论持仓和收益；Python 通过 `WtBtEngine → WtBtWrapper → WtBtPorter → ExpCtaMocker` 接入。这使研究复用策略方法，减少另写一套算法的漂移。实时运行则依赖到达顺序、柜台异步回报、实际订单和账户快照。

| 验证层 | 能回答的问题 | 不能据此推出 |
|---|---|---|
| 历史回测 | 在指定数据、成本和成交模型下，规则怎样表现 | 真正盘口成交、断线和保证金机制已通过 |
| 本地 TraderMocker | 行情、执行、模拟回报与状态链能否联动 | 真实 CTP 协议和资金账已通过 |
| SimNow | API认证、查询、订阅、异步委托与回报是否正确 | 实盘流动性、成本和长期盈利完全相同 |
| 实盘小规模试运行 | 实际成交、成本、风险与运营质量 | 更大资金或更多策略仍保持同等效果 |

成交模型把“这个历史事件允许怎样成交”的决定从 CtaMocker 的持仓、费用和输出处理中分开：模型负责时序、价格和数量约束，账本负责把成交作用于仓位与损益。好处是旧模型与新语义可比较，代价是必须明确事件和预算契约。`causal_touch` 的下一行情触价规则也不等于恢复完整订单簿或模拟队列优先级，详见[06 成交模型与面试表达](06_成交模型与面试表达.md)。

比较成交假设时还要区分固定目标回放和闭环策略：固定目标有助于隔离执行成本；闭环策略会读取仓位并改变后续决策，当前新增模型的输入过滤也可能改变策略看到的事件。因此不能声称“改模型一定不影响信号”。

业务评价要分开两组指标：策略看样本外净收益、回撤、换手和资金占用；执行看成交率、相对决策价格的偏差、等待时间、撤单与拒单、未完成量。执行更稳定可能减少损失，却不能把无优势的信号变成有优势的策略。当前人工功能路径正收益168元，历史五分钟诊断净亏542元；它们的数据和目的不同，均不证明当前一分钟策略能赚钱。

## 7．产品化路线：先把一套有限场景做成闭环

### 先定义谁会使用、为哪个结果付出成本

产品化不必先变成对外网站。把自己的研究和模拟流程变成可重复使用、可支持的工具，也是一个有边界的产品。

| 候选产品 | 用户的真实问题 | 交付与价值衡量 |
|---|---|---|
| 个人研究/模拟工作台 | 环境难装、配置容易串、回测与模拟结果难解释 | 固定运行包、数据与结果目录、明确观察/交易入口；衡量从准备到可观察运行的步骤、首次成功率和定位问题耗时 |
| 团队内部交易运行台 | 多策略共享账户，风险、权限、账目和责任难分清 | 沿用 WT 引擎/执行器/监控，补统一预算、对账、角色和审计；衡量无法解释的仓差、误操作、恢复时间与支持成本 |
| 对外部署与维护工具 | 使用者不会排查 SDK、交易时段、断线和版本问题 | 明确支持的柜台/平台/策略范围、可升级运行包和服务流程；先用真实用户试用检验需求及交付成本 |

对当前项目，建议先交付第一种，再判断是否存在第二种的真实需求。不要一开始同时承诺多账户、多柜台、多资产、无人值守；每新增一种组合，都要承担规则、运行和支持成本。

在写代码前先把业务承诺写成一句可检验的话，例如：“帮助一个账户在明确交易窗口内，观察指定品种的行情和策略目标；只有对账通过才允许执行，异常时能解释当前订单与仓位。”这比“打造全自动量化平台”更容易验收。

需求验证可从你自己的一次完整使用开始：哪些步骤必须人工介入、哪里最容易错、什么状态让你不敢继续、哪份输出让你无法判断结果。再由少量目标使用者照着操作，记录阻塞和支持时间。先解决反复出现的业务问题，再扩展功能；盈利承诺不作为工程工具的默认卖点。

产品成本不只是服务器：还包括行情质量与使用授权、柜台差异、数据与状态恢复、版本升级、故障支持及结果解释。对外提供时要逐项明确支持范围、数据使用边界和责任；本文没有设计代客交易业务或给出商业经营资质结论。

### 用已有模块逐步交付

WT 已具备交易框架的重要部件，但“有模块”到“普通用户可稳定使用”之间，还需要明确支持场景、配置契约、状态展示和故障处理。推荐围绕当前小资金、单品种、单策略 CTA 场景推进，先不扩成多账户、多柜台、多资产平台。

| 阶段 | 建议交付 | 可验收指标 / 证据 |
|---|---|---|
| A：可复现装配 | 固定运行包、显式工作目录、必要配置说明、启动前校验 | 目标合约/时段/费用映射完整；必需插件可加载；账户和路径无歧义；不继承旧实验持仓 |
| B：持续行情闭环 | 中台接收→存储→Runner→Python 策略 | 各段计数与最后更新时间可观察；目标合约持续变化；主 K 线闭合和计算次数对应；异常有具体原因 |
| C：订单闭环 | 一手开平、正常成交、拒单、撤单和部分成交处理 | 每个委托可关联 localid、柜台订单号和成交号；最终未完成量归零；柜台实际持仓与预期相符 |
| D：恢复与停机 | 正常退出、断线重连、带仓重启、交易日切换 | 无回调访问已销毁对象；最终检查点完整；重启对账后才放行；不重复报单或意外清仓 |
| E：运行控制 | 观察模式、禁新仓、禁所有新增委托、受控退出仓位、监控权限 | 操作者能区分各动作；状态进入日志；关闭策略不误等于账户已平仓；资金/行情过期时实际限制生效 |
| F：持续研究 | 成交模型、历史数据质量、成本和执行差异分析 | 样本外结果、费用假设、成交边界与实盘偏差分别报告；没有把历史拟合收益写成未来盈利保证 |

这些指标应按场景产生证据，不要求每次文档或配置小改动全量回归。改 SDK 验证 API 加载、认证、订阅/查询和受影响的订单回报；改执行器则检验对应目标、未完成量和撤单分支；改教程检查命令、路径与说明。

指标的数值阈值需要根据目标业务和实测制定。例如行情过期多少秒、回报等待多长、重连多久后停止新仓，都不能凭框架名称断言。性能报告应标明机器、策略数、订阅数、数据速率、统计窗口和时钟来源，再给分位延迟与丢失/积压计数。

### 当前特别值得优先补的边界

1. **配置错误早失败。** 缺品种会话、初始化返回 false、库入口缺失，应在启动阶段报告具体组件并停止依赖它的交易路径。目前仍有把交易接口 init 失败误报为 deleteTrader 缺失、部分 Adapter 失败后继续注册的行为。
2. **统一两套入口的生命周期。** C++ WtRunner 与 wtpy WtRtRunner 的退出不同，先建立明确的 stop / release 契约，再验证 Python 带仓恢复。
3. **理论账和实账对账。** 不能拿策略 CSV 直接当柜台收益；不能拿全 0 的 TraderMocker 资金占位当保证金模拟。
4. **资金与行情新鲜度。** 当前 CTA 分钟调度和实际成交后会请求柜台资金，但不代表异常期间持续刷新；检查有效快照，明确未取得资金时的交易限制。
5. **接口与数据边界可观察。** 单独记录连接、认证、登录、查询和 ready；行情记录远端时间、本机时间、接受/过滤原因和下游处理情况。

上面是建议的工作优先级，不是本次已经修复这些缺口。

### 当前不能省略的恢复与权限边界

`simnow-03` 要求交易状态目录全新，是首轮空仓试验的保守门禁：它防止旧 C++ 目标在 Python 放行之前执行，也会失去旧 userdata 中的当日次数、日初损益和冷却。当前不能称为跨重启账户级日内风控。下一步应保留独立的账户风险状态，在对账门禁内恢复策略与执行状态；不能通过反复新建目录获得新的风险额度。

监控的 SQLite 保存用户、组合路径和调度，交易账另读 JSON/CSV。已有登录界面不等于多人操作权限已经闭环：当前 `WtMonSvr.cmd_start_app/cmd_stop_app/cmd_commit_group_file` 检查登录后，未在这些路径核对相应管理员角色或组合授权。进入团队产品前，要让观察者、操作者和管理员的权限在服务端实际执行，并使 HTTP 和 WebSocket 使用一致规则。本轮是源码定位，未运行权限攻击实验或修改鉴权，详见[07 监控与SQLite](07_wtpy监控与SQLite.md)。

<details markdown="1">
<summary>展开：一处订单事件幂等风险，为什么产品化要单独检验</summary>

当前 VM `TraderAdapter::onPushTrade` 先增加实际持仓、更新未完单并通知执行器，之后才调用 `checkSelfMatch`。下面按原顺序摘出开多分支与后续语句，中间省略了其他方向和统计代码：

```cpp
// TraderAdapter::onPushTrade：原代码关键顺序
pItem.l_newvol += vol;  // 开多分支
// ... 后续更新未完成量 ...
for (auto sink : _sinks)
    sink->on_trade(localid, stdCode.c_str(), isBuy, vol, tradeRecord->getPrice());
// ... 记录 CSV ...
checkSelfMatch(stdCode.c_str(), tradeRecord);
```

`checkSelfMatch` 的主要用途是检测自成交；相同成交号与关联订单的重复回报分支没有撤销前面的持仓影响。因此若同一成交被重复送入这一入口，当前路径不能保证只记账一次。**这是已定位的静态路径风险，未注入复现；不能写成 SimNow 本轮真的重复成交。**

产品化方向是在改变账户状态之前，依据柜台协议定义的订单/成交标识检查事件是否已处理，区分快照和增量，再检验重复、乱序、撤单/成交竞态和重连查询。这里给出设计方向，没有提交幂等修复。

</details>

## 在线回测网站：把回测能力变成产品

**在线回测算产品化，而且可以复用现有 WT。** 它让使用者在浏览器编辑策略、选择行情和参数、提交回测，再查看日志、净值和交易记录。核心价值是降低环境准备成本，让研究能重复、结果能解释。下面是后续方案，网站尚未实现。

例如使用者今天修改一个均线参数，下周希望与原结果比较，平台应能找回两份代码和同一数据范围，而不用重新猜当时装了哪套库。学习者能从可运行模板开始，研究者能保存实验并对比结果，维护者能从任务日志定位失败。这些可反复完成的事情，才构成实际用户价值。

**网站要补管理和体验，回放与记账继续交给 WT。** 已有 `WtBtEngine→WtBtPorter→HisDataReplayer→CtaMocker`，以及 Python 策略回调、成交模型、CSV输出和分析器，可以直接复用。新增部分是编辑器、教程、任务队列、数据集选择、进度、取消、错误说明、结果展示和访问权限。现有 `WtBtMon` 用子进程启动 `runBT.py`，是可参考的任务雏形；它还不等于完成了多人执行隔离与资源管理。

使用流程应保持简单：提交后立即得到任务号，页面显示“排队、运行、完成或失败”；任务结束仍能找回策略、配置、日志和结果。一次失败应告诉使用者是代码错误、缺数据还是超时，不能因为程序退出码为0就显示成功。收益曲线应取自已有账本；平台选择的分析本金是收益率分母，不应描述为回测已实施保证金约束。

网页刷新只影响显示，不能让任务重新提交或停止；再次点击运行应得到一项新的、可区分的实验。当前底层回调异常未统一变成任务失败对象，平台还需记录策略异常、数据初始化和回放完成状态。任务管理器应保留失败原因，下载接口检查结果属于哪个用户，避免把别人目录中的文件当作当前任务产物。

**API手册要教会使用者表达策略。** 普通 Python CTA 的计算回调是 `on_calculate(self, context)`，先在 `on_init` 指定主K线；开多是 `context.stra_enter_long(...)`，直接指定目标用 `stra_set_position(...)`。当前多1时，enter_long 1 请求增加多仓，set_position 1 则仍以多1为目标。回测中的请求还要经过成交模型，不能把调用当作已成交。手册应展示初始化、主K线、信号、目标、成本和结果的一套例子，解释无报价、等待成交、部分成交及反手；只列签名会让初学者不断试错。

一篇好的入门例子应先订阅一分钟主K线，再检查可见历史是否足够，最后按条件设置多、空或零目标。旁边解释什么时候触发计算、历史切片能看见哪些数据、为什么不是每根K线都开一手。接口页面还应说明参数单位、标准合约代码、返回值及空数据处理，并链接最小示例与对应结果，帮助使用者把函数与业务串起来。

**一项任务用一个新进程，避免共享引擎状态。** Python `WtBtEngine` 和 Wrapper 有 singleton，原生 `getRunner()` 也返回静态Runner；它们不是多用户任务容器。在Web进程中为两个用户各构造一个engine，可能共享配置、回调和输出。可让任务管理器启动独立worker，每项任务拥有自己的工作目录、配置、日志与结果；历史DSB只读共享。库可以共用，不必每项任务复制或编译。CSV模式可能写缓存，需先整理数据或把缓存分到任务目录。

能执行用户Python，就需要管理它可能占用的资源和接触的文件。worker应限制CPU、内存、进程数、运行时长和输出大小；只读挂载所选历史数据，仅允许写任务目录，默认关闭不必要的网络，不提供交易账户密钥、宿主根目录或Docker控制接口。取消先尝试正常停止；无响应时终止该任务，标为取消或超时，不能把不完整结果标为成功。

**Docker只是其中一层隔离。** 官方文档分别讨论命名空间、资源控制、守护进程、挂载和权限，并指出配置与内核风险。因此不能说“放进Docker就能安全运行任意代码”。公开服务还要评估更强隔离，检验文件、网络和进程边界，升级宿主与运行环境；简单禁几个import也不能代替这些工作。[Docker 官方安全说明](https://docs.docker.com/engine/security/)

结果要带上策略快照、参数、数据集版本、Python包与C++库版本、成交模型、滑点及费用。比较两次回测时，先确认这些条件是否一致。保留原始CSV和审计，再生成网页图表；同一目标的等待、拒绝和覆盖不能算作成交次数，也不要把理论成交假设写成真实排队能力。任务ID和明确版本登记已能解决基本追踪，无需额外造一套哈希流程。

数据选择也要便于理解：展示覆盖日期、合约、分钟或Tick类型、是否有真实盘口以及缺失情况。用户通过数据集编号选择，平台映射只读路径，不接受任意服务器目录。只有分钟数据时，页面应解释成交模型的限制；样本外与样本内结果应分开保存，避免把反复调参得到的历史优势当成已经验证的预测能力。

落地建议分三步。第一步做自己的私有网站，只支持固定CTA模板、少量合约和已准备的数据，先打通提交、报错、取消、结果下载，并能重跑解释一致的结果。第二步给小团队使用，增加任务所有权、并发配额、资源限制、版本管理和共享规则，确保别人看不到或改不了不属于自己的任务。第三步再考虑公开注册、使用授权、数据服务成本、隔离强度和故障支持；进入下一步应以实际使用和验收为依据。

第一步可以用有限的真实任务验收：一份正常策略、一份语法错误策略、一项无数据任务和一项超时任务，检查页面是否给出正确状态与原因；再核对图表和原始CSV。小团队阶段再验证并发任务不串配置、日志和结果。公开阶段需要重新审视用户代码与宿主隔离，不能拿单用户测试通过代替公开服务的运行承诺。

这条路线把已会运行的研究工具变成别人也能理解和使用的服务。网站成功的指标是任务与结果可靠、错误清楚、操作可控、研究效率提高；它不能承诺用户策略盈利，也不代表模拟盘和实盘系统的验收已经完成。

## 8．面试时怎样讲得具体而不过度

### 面试追问，怎样把技术选择连到业务

| 常见追问 | 可以展开的理由与代价 |
|---|---|
| 为什么中台与策略分进程，插件却不拆服务？ | 行情被多个策略复用，分进程允许独立积累数据；进程内插件减少序列化和接入复杂度，代价是插件崩溃会影响宿主。当前有限场景先利用这些边界，是否进一步隔离由故障与负载证据决定。 |
| 为什么用UDP或SHM？ | 适合本机/局域网的一对多快速分发；UDP易部署，SHM可减少跨进程传输复制。代价是可靠交付、覆盖与发布顺序要另外检验；本轮没有得到可宣传的延迟或不丢数据保证。 |
| 为什么用mmap、CSV/JSON，又有SQLite？ | 高频行情、顺序分析输出、恢复快照、运维用户配置的访问模式不同。mmap支持共享读取，CSV易分析，JSON易表达检查点，SQLite提供管理数据事务查询；代价是跨文件一致性与恢复时刻需要明确，文件存在不能证明业务提交完整。 |
| 为什么先做CTA，真实成交不直接回给Python策略？ | 当前一分钟目标策略适合信号与执行分开，执行层统一管理柜台回报。业务若必须逐委托调整，应评估HFT等订单接口，而不是用CTA理论仓猜实际成交。 |
| 如果让你变成产品，最先改什么？ | 先让环境与放行条件可见，打通观察、订单、对账和恢复；复用现有引擎与监控，补账户预算和操作权限。每一步给出业务承诺、异常行为和证据，暂不扩张支持范围。 |

可以先讲业务问题，再讲分层，再用一个源码调用和一个实测现象证明理解：

> 我把 WT 理解为统一行情、策略目标、执行与柜台状态几个层次。行情中台提供同一份实时和历史数据；CTA 策略输出目标仓位，组合汇总后交给执行器。执行器结合柜台实际持仓与未完成订单决定怎么拆单、定价和撤单，TraderAdapter 负责开平规则与通道状态，TraderCTP 负责协议转换。策略理论成交与柜台真实成交分开保存，因此我会同时检查两本账和执行偏差，不能只看策略收益。

接着说与你实际工作相符的部分：

- SDK 适配中，核对了创建函数签名和导出符号，隔离编译 ParserCTP、TraderCTP、CTPLoader，并验证接口流程。
- 本地模拟过程中，发现了累计成交量、日期字段、退出线程和持仓恢复等具体语义问题；只把已经修复并有证据的范围说成完成。
- 回测成交模型的改造，讲清历史事件、成交限制、量预算与费用边界，再说明它不等同于真实订单簿仿真。
- 产品化下一步以行情、订单、恢复和对账闭环为目标；不把“登录成功”扩写成“实盘系统全面可靠”。

如果问“你的系统低延迟吗”，给实际测量或说明尚未测量。如果问“策略能赚钱吗”，给数据范围、费用、样本外表现和未知风险，不能从框架架构推导盈利。架构能力、工程验收与投资表现是需要分别证实的三件事。
