# run目录异常文件名与simnow03当前运行模式

核对时间：2026-10-15 21:18（北京时间）。本次只读检查VM现有文件、启动配置和源码；没有启停程序、下单、删除异常文件、修改编码或部署源码修复。

**结论：run根目录确有历史异常文件名，不是简单的编辑器编码设置问题；当前simnow03仍是CTP观察入口，没有启用策略下单。监控大部分数据页面读generated输出，只有配置管理等页面直接读启动配置。**

## 1．“无效编码”具体是什么

本次发现8个异常空目录和8个异常JSON文件。部分文件名含非UTF-8字节，另一些虽然可按UTF-8解码，却包含退格等控制字符。它们在文件管理器、编辑器和终端中可能显示为乱码、方框或“无效编码”。

例如某个文件名的开头原始字节为`01 ab 3a 15`，后面接`ud_one_lot_acceptance.json`。这里用十六进制表示，避免把控制字符直接写进教程。

| 核对项目 | 实际结果 | 说明 |
|---|---|---|
| 异常条目 | 8个空目录、8个JSON文件 | 异常主要在文件名与输出位置 |
| 8个JSON内容 | 都能严格按UTF-8解码并解析JSON | 文件名异常，不等于内容也乱码 |
| JSON结构 | 策略状态、userdata或组合状态 | 与WT保存函数的输出结构对应 |
| 修改时间 | 10月14日21:51:25、21:53:45、21:55:36、21:58:55附近 | 与当晚多次进程结束时间吻合，早于监控部署 |
| 顶层正常Python/YAML文本 | 17个均能严格按UTF-8解码 | 没有依据把整个目录批量转码 |
| 当前通道CSV | 本次样本可按UTF-8与GB18030解码 | 不能据此认定所有历史中文CSV都是UTF-8 |

正常情况下，相关文件应出现在：

```text
generated/
├─ stradata/<策略ID>.json
├─ userdata/ud_<策略ID>.json
└─ portfolio/datas.json
```

现在部分文件落在run根目录，并且原本应为目录前缀的部分变成短随机字节，后面的`策略ID.json`、`ud_策略ID.json`或`datas.json`仍可识别。这更符合保存路径出错的现象，不能通过给文件内容换一种编码来修复。

另外，`CTPTDFlow`中的CTP流文件可能是二进制，`monitor.ipc`是IPC通信端点；这类条目不应按普通UTF-8文本阅读，也不能与异常JSON文件名混为一谈。

## 2．源码指向什么原因

已经定位到对应的保存调用：`CtaStraBaseCtx::save_data()`、`save_userdata()`和`WtEngine::save_datas()`。它们通过`WtHelper`取得目录，再拼接策略名或`datas.json`。

<details class="source" markdown="1">
<summary>展开实际路径保存代码</summary>

`src/WtCore/WtHelper.cpp`缓存路径的方式为：

```cpp
const char* WtHelper::getStraDataDir()
{
    static std::string folder = StrUtil::standardisePath(_gen_dir) + "stradata/";
    if (!StdFile::exists(folder.c_str()))
        boost::filesystem::create_directories(folder);
    return folder.c_str();
}
```

userdata、portfolio等目录也采用同类函数局部静态字符串。策略状态与用户数据保存函数分别拼接：

```cpp
// CtaStraBaseCtx::save_data()
std::string filename = WtHelper::getStraDataDir();
filename += _name;
filename += ".json";

// CtaStraBaseCtx::save_userdata()
std::string filename = WtHelper::getStraUsrDatDir();
filename += "ud_";
filename += _name;
filename += ".json";

// WtEngine::save_datas()
std::string filename = WtHelper::getPortifolioDir();
filename += "datas.json";
```

</details>

**高度可疑的原因是退出时的静态对象析构次序。** WtPorter的Runner是函数局部静态对象，目录缓存通常在Runner创建之后、初始化和运行过程中才首次构造。进程结束时，后构造的目录字符串可能先析构，而Runner成员引擎随后才析构，并再次触发终态保存。

```text
先构造静态Runner
  → 运行中构造静态目录字符串
  → 进程退出，目录字符串先析构
  → Runner / CTA Engine随后析构
  → stop()补保存策略、userdata、组合状态
  → 再访问已结束生命周期的目录字符串
```

目录字符串的底层内存释放后，若继续用于拼文件名，前缀可能变成分配器元数据等无效字节；后拼接的策略名仍然正常。这能解释当前“随机前缀＋正常JSON后缀”和同前缀空目录的形态。

这里的关键是**对象寿命**，不是简单地把`.c_str()`改成别的写法。函数局部`static std::string`在正常运行中有效；问题出在它析构后仍可能被退出保存逻辑访问。

<details class="source" markdown="1">
<summary>展开静态Runner、退出保存及release边界</summary>

`src/WtPorter/WtPorter.cpp`：

```cpp
WtRtRunner& getRunner()
{
    static WtRtRunner runner;
    return runner;
}
```

当前工作区的`WtCtaEngine::~WtCtaEngine()`会调用`stop()`；后者在停止线程后补存各上下文与组合：

```cpp
// WtCtaEngine::stop()的保存片段
if (_tm_ticker)
{
    for (auto& item : _ctx_map)
    {
        auto ctx = dynamic_cast<CtaStraBaseCtx*>(item.second.get());
        if (ctx)
            ctx->flush_state();
    }
    save_datas();
}
```

`flush_state()`依次调用`save_data()`和`save_userdata()`。但`WtRtRunner::release()`目前主要停止日志：

```cpp
void WtRtRunner::release()
{
    WTSLogger::stop();
}
```

因此不能认为Python调用`engine.release()`就已经在目录缓存有效期间完成了整个运行器的有序关闭。这也是此前一直保留“Python完整关闭未验收”的原因。

</details>

**验证边界：** 异常文件、时间和JSON结构已确认；保存路径和静态对象风险链已经通过源码核对。历史进程没有保留该错误的调用栈，本轮没有新增独立退出复现或ASan验证，因此不能宣称已对每个历史文件完成运行时归因，也没有把它标为已修复。

此前为C++本地模拟增加的停止与终态保存，不能直接等同于Python桥接运行器的完整退出也已经解决。这是已有修复在当前场景中仍需处理的边界。本轮先保留原文件作为证据；不能把批量删除、改名或转码当成源码修复。

## 3．simnow03现在究竟能不能自动下单

**当前监控登记的是观察入口。** 它连接的是已配置的SimNow第一套环境，交易模块是`TraderCTP`；但目前没有启用“策略目标→执行器→报单”的链路。

| 检查项 | 当前实际值 | 作用 |
|---|---|---|
| 监控启动参数 | `python run.py` | 没有`--trade` |
| `run.py` | 拒绝额外参数，再调用`run_live.main()` | 固定使用默认观察入口 |
| `run_live.py` | `--trade`为`store_true` | 不传时为False |
| 实际选择主配置 | `config.ctp-observe.yaml` | 选择观察配置 |
| `config.yaml`链接 | 同样指向`config.ctp-observe.yaml` | 与监控配置树当前显示一致 |
| 执行器文件 | `executers.observe.yaml`，`executers: []` | 没有加载CTA执行器 |
| Python策略 | `armed=False`，只有交易分支通过门禁才会置True | 未授权产生交易目标 |
| 交易接口 | 活跃的`TraderCTP` | 仍能连接柜台、查询持仓资金和接收回报 |

所以，“看得到CTP资金、交易通道已ready”不代表“策略已开启自动下单”。`datmod=auto`也只是监控实时展示设置，不是交易开关。

目录内另有`config.ctp-trade.yaml`和`executers.trade.yaml`，供后续明确启用交易的入口使用；它们存在于磁盘不等于已经加载。现有`run.py`不能直接追加`--trade`，因为它会拒绝额外参数。真正切换还需要正确的启动入口、交易配置、执行器及账户检查门禁，本轮没有替用户切换。

后续启用这套TraderCTP执行链时，订单会发送到配置的SimNow柜台模拟环境；本地撮合使用的是另一种接口`TraderMocker`。两种模拟方式应分别理解。
