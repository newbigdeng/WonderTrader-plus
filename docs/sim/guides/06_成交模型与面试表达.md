## 1．成交模型到底做了什么，初始化要不要读取配置

### 4.1 模型的边界：目标到模拟成交的假设

模型决定“这条回放事件能不能成交、能成交多少、按什么基础价格”。它不生成 CTP 报单，不接受真实柜台成交回报，不维护交易所排队位置。持仓明细、开平拆分、费用和盈亏由 `CtaMocker::apply_fill` 与播放器的 `calc_fee` 处理。

| 模型 | 时序 | 价格 | 数量 |
| --- | --- | --- | --- |
| `legacy_cta` | 保留原 CTA 回测处理顺序，目标差额立即记账 | 原基准价路径及原滑点逻辑 | 一次处理全部差额 |
| `causal_touch` | 至少等目标创建后的下一合格事件；可再等额外事件 | 买 ask1、卖 bid1，叠滑点、对齐跳动、检查涨跌停 | 全部差额，未按盘口挂量限量 |
| `volume_limited` | 复用 causal 门槛 | 同 causal | 以真实 Tick 增量×参与率预算，允许部分成交 |

待成交目标按合约保存最新目标。每次的剩余量都重算 `target - actual`，而不是另存一份累计剩余；同值目标重申保留创建事件序号，不同目标覆盖旧目标。策略把目标改成当前实际仓位就会取消余下目标。

关键数量规则，VM `CtaFillModel.cpp:193—214`：

```cpp
const double raw_budget = volume * _participation_rate;
const double available = std::floor(raw_budget) - used;
if (available <= 0.0) { /* NoLiquidity */ }
const double magnitude = std::min(std::abs(result.signed_delta), available);
result.signed_delta = std::copysign(magnitude, result.signed_delta);
```

例如目标 10 手、当前 0、市场 Tick 新增 71 手、参与率 10%，预算 7 手，本次实际到 7，剩余 3 等后续事件。同一个 `handle_tick` 内，原链路会在策略回调前后两次检查目标；新增预算账本确保两次不能把同一笔市场量重复用掉。扣预算按**记账后的实际仓位变化**，而不是盲目按模型建议量扣。

时序核心，VM `CtaMocker.cpp:1124—1210`：

```text
有效 Tick 输入 → 更新事件序号与报价快照
 → 验证真实新增量（限量模型）
 → proc_tick 检查旧目标
 → 策略 on_tick，可能生成/覆盖目标
 → proc_tick 再检查，仍是同一事件与同一预算
 → 记录事件末权益
```

`CtaTickVolumeSource` 用 `total_volume` 差分验证 Tick 的 `volume`；同交易日第一条只建立基线不给预算，换交易日重新建立基线。零量、量源不符、重复或乱序等情况不能冒充可成交量。该预算是一种研究假设，市场成交量不保证你的委托有相同比例可成交。

真正的记账核心，VM `CtaMocker.cpp:2042—2046`：

```cpp
const double actual_before = pInfo._volume;
const double actual_after = actual_before + fill.signed_delta;
const double final_price = apply_fill(stdCode, actual_after,
    userTag, curTm, curTDate, fill);
```

`apply_fill` 仍使用品种乘数计算盈亏，按开平与平今调用 `HisDataReplayer::calc_fee`，再写 trades/closes/funds。模型处于 WaitingLatency、NoQuote、NoLiquidity 等状态时，不会进入记账，不会提前产生仓位和费用。

### 4.2 初始化有配置，但不必新增一个专门 YAML

Python策略通过 `set_cta_strategy(fill_model=..., event_delay=..., participation_rate=...)` 将参数传给 C ABI。C++ `initCtaMocker` 先创建对象，再 `configure_fill_model` 校验参数，成功后加载所需增量状态和注册播放器 sink。程序化 Python 路径不是模型自己去找磁盘文件。

若使用 C++ 策略工厂回测，则 `CtaMocker::init_cta_factory` 从策略配置节点读取 `model`、`event_delay`、`participation_rate`，最后调用同一个配置入口。整体回测 YAML 仍用于行情、日历、手续费等设置。

| 参数 | 当前契约 |
| --- | --- |
| `fill_model` | 上述三个名称；默认 `legacy_cta` |
| `event_delay` | 非负 uint64 事件数；0 也要求 causal 等下一事件；legacy 必须0 |
| `participation_rate` | 限量模型要求有限数且 `0 < rate <= 1`；另外两模型必须0 |
| `slippage`、`isRatioSlp` | 固定跳动或比例滑点；新增价策略只叠一次 |

Legacy 用原 `init_cta_mocker`；causal 用 v2；volume 用 v3。Python 会检查库是否有对应符号，缺符号或参数错误会报错，没有静默切回 legacy。两端版本必须配套。

### 4.3 面试可以这样讲

> 我将 CTA 回测原来“目标差额直接成交”的逻辑抽成可替换决策接口，保留原账本和默认 Legacy 行为。新增下一事件按买卖一成交，以及按真实 Tick 增量与参与率限量的模型。目标状态按合约保存最新值，部分成交后按实际仓位重算剩余；事件预算防止同 Tick 前后两次撮合重复使用市场量。增加决策和实际成交审计，用仓位、数量、费用与资金守恒核对结果，并保留默认 CSV 与基线的兼容验收。我把这些当成成交假设的敏感性研究，不宣称等同实盘。

需诚实补充当前边界：没有交易所排队、主动成交方向、冲击反馈或保证金拒单；小数目标仍可能导致非整手成交；浮点参与率取整与逐 Tick 切分敏感；增量恢复未保存完整量源/过滤/预算，不能宣称任意断点等价；输入过滤比较字段不完整；逐 Tick 审计在内存累积，有长周期资源压力。2026-09-30 已有组件测试、Legacy 原五份 CSV 对照、单日 Tick 验收和参数矩阵记录，但本次文档重写没有重新执行它们。
