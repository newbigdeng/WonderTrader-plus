## 1．先分清三个程序与三种场景

**LoaderRunner 不接收行情。** 它连接的是 CTP 交易接口，认证、登录以后查询合约，把合约属性整理为 WT 的品种与合约 JSON。查询完成就退出，不需要作为模拟盘的第三个常驻进程。

**QuoteFactory 是行情生产者。** 它通过 ParserCTP 等插件接行情，交给 WtDataWriter 更新实时文件与 K 线，并向 Runner 广播。它不代替 TraderCTP 下单。

**Runner 是策略与交易的组织者。** 它从 ParserUDP 或 ParserShm 收行情，调度策略，把策略目标交给执行器。执行器通过 TraderCTP 或 TraderMocker 接口完成交易。

| 场景 | 行情来源 | 下单目的地 | 撮合发生在哪 |
|---|---|---|---|
| 本地模拟盘 | 实时行情，或专门准备的行情回放 | TraderMocker | 当前进程的模拟交易接口 |
| SimNow 模拟盘 | SimNow 行情→QuoteFactory→Runner | TraderCTP→SimNow 交易前置 | SimNow 服务端 |
| 实盘 | 行情柜台→QuoteFactory→Runner | TraderCTP→期货公司实盘前置 | 柜台与交易所 |
| CTA 回测 | 历史数据播放器 | CTAMocker 的历史成交模型 | 回测引擎内部 |

同一个 `TraderCTP` 插件既可接 SimNow，也可接实盘；决定目的地的是前置地址、账户和认证参数。`TraderMocker` 与回测的 `CTAMocker` 是不同组件，不能用回测成交模型的改造解释本地模拟接口行为。

常规运行拓扑：

```text
CTP 行情 API
  → ParserCTP（转换为 WT Tick）
  → QuoteFactory 的 ParserAdapter / DataManager
  → WtDataWriter（快照、实时 Tick、K 线、可选 CSV）
  → UDPCaster 或 ShmCaster
  → Runner 的 ParserUDP 或 ParserShm
  → WtCore::ParserAdapter
  → WtCtaEngine / WtCtaRtTicker
  → CTA 策略上下文
  → 策略目标仓位
  → 过滤器 / 组合风控 / 执行器路由
  → WtLocalExecuter / WtMinImpactExeUnit
  → TraderAdapter（开平规则、持仓、订单、流控）
  → TraderCTP → CTP 交易 API → SimNow
         或 TraderMocker → 本地撮合
```


## 2．LoaderRunner 怎样生成基础 JSON

源码入口 `src/LoaderRunner/LoaderRunner.cpp` 的实质很短：

```cpp
// 摘录：参数默认 CTPLoader 模块 / config.ini
LoaderRunner runner = (LoaderRunner)DLLHelper::get_symbol(handle, "run");
return runner(cfgfile.c_str(), false, true);
```

它是加载器宿主，真正的业务在 `CTPLoader::run` 与 `CTraderSpi`。`config.ini` 给出：交易前置、账户认证、输出 `path`、品种/合约文件名、产品类别 `mask`、`mapfiles` 等。

调用链为：

```text
LoaderRunner → dlopen(libCTPLoader.so) → run(config.ini)
→ 创建 CTP TraderApi、RegisterSpi、RegisterFront、Init
→ OnFrontConnected → ReqAuth
→ OnRspAuthenticate 成功 → ReqUserLogin
→ OnRspUserLogin 成功 → LoadFromJson → ReqQryInstrument
→ OnRspQryInstrument（每个合约一条回调）
→ 最后一条回调 → DumpToJson → exit(0)
```

`OnRspQryInstrument` 从 CTP 合约字段取得交易所、合约/品种标识、乘数、最小跳价、数量范围、上市和到期日期、多空保证金比率等。它结合本地 `map*.ini` 生成 WT 品种名称、交易时段、开平等信息，按输出目录写 `commodities.json`、`contracts.json`。

**交易时段模板不会因查到一个新品种而自动变正确。** `MAP_SESSION[交易所.品种]` 查不到时，`session` 可能为空。此前查到 87 个品种、852 个合约不等于 WT 可以加载全部品种；缺时段映射的问题必须另外补齐。不要把 query 的成功当作数据完整性验收。

它不产生 Tick、不产生 K 线、不填 `FUT_Data`。也不从行情服务推断历史数据。用于稳妥更新时，输出到临时 `common.incoming`，核对映射和目标合约后，再发布到 `common`。


## 3．中台接行情、mmap、CSV 与历史归档

`QuoteFactory::initialize()` 依次加载基础 JSON，初始化 SHM/UDP caster 并注册到 DataManager，准备状态机，创建 Writer，可选初始化指数工厂，最后创建并连接行情 parsers、启动状态机。

ParserCTP 登录后订阅合约；`OnRtnDepthMarketData` 将 CTP 结构转换成 `WTSTickStruct`：交易日、自然日、行情时间、最新价、累计量额、持仓量、五档买卖价量等，交给中台 `ParserAdapter::handleQuote`。

处理链：

```text
ParserCTP::OnRtnDepthMarketData
→ WtDtCore::ParserAdapter::handleQuote
→ 查到 WT 合约/品种；缺日期或缺合约则拒绝
→ DataManager::writeTick
→ WtDataWriter::writeTick
→ 同步 procTick，或入任务队列由线程 procTick
→ 判断会话可接收
→ updateCache → pipeToTicks → pipeToKlines → broadcastTick
```

核心顺序在虚拟机 `src/WtDataStorage/WtDataWriter.cpp:400`，摘录如下：

```cpp
if (!_sink->canSessionReceive(commInfo->getSession()))
    break;
if (!updateCache(ct, curTick, procFlag))
    break;
if (!_disable_tick)
    pipeToTicks(ct, curTick);
pipeToKlines(ct, curTick);
_sink->broadcastTick(curTick);
```

所以“已经订阅成功但没有文件”，仍可能因为无远端推送、合约无法解析、交易时段过滤、时间字段异常或保存开关。当前广播处于 Writer 处理成功之后：被会话过滤的 Tick 不会在这一正常链路继续广播。

典型数据目录：

```text
FUT_Data/
├─ cache.dmb                       每合约的最新 Tick 快照
├─ rt/
│  ├─ ticks/SHFE/rb2701.dmb         当日 Tick，mmap 实时块
│  ├─ ticks/SHFE/rb2701.日期.csv     savelog=true 时附加的阅读日志
│  ├─ min1/SHFE/rb2701.dmb          实时 1 分钟 K 线
│  └─ min5/SHFE/rb2701.dmb          实时 5 分钟 K 线
├─ his/
│  ├─ ticks/SHFE/交易日/rb2701.dsb  按日历史 Tick
│  ├─ min1/SHFE/rb2701.dsb          历史 1 分钟 K 线
│  ├─ min5/SHFE/rb2701.dsb          历史 5 分钟 K 线
│  └─ day/SHFE/rb2701.dsb           日线
└─ 状态标记等辅助文件
```

`.dmb` 不是纯粹的匿名内存：程序先创建/扩容磁盘文件，再通过 `BoostMappingFile`→`boost::interprocess::file_mapping` / `mapped_region` 把它映射到地址空间。写 Tick 是向映射区的结构数组 `memcpy`，增加块头 `_size`；容量不足时扩容并重映射。修改进入操作系统页缓存，由映射 flush 和系统写回机制持久化；不能理解为每个 Tick 都执行一次同步磁盘刷盘，也不能保证断电最后一条必然持久化。

Reader 以只读映射读取 `rt`，按需加载/解压 `his`，合并历史和实时数据。`data.store.path` 必须指向中台 Writer 的同一行情根目录；仅收到 UDP 并不能自动发现磁盘路径。

`writer.savelog` 开启的 Tick CSV 是附加文本日志，当前字段包含 code、交易日/自然日/时间、本机接收时间、价格、量额、持仓等，**不含完整五档盘口**。不能拿这种阅读日志直接当完整 Tick 回测数据，尤其不能由它证明真实买卖盘口与排队情况。

收盘归档由 StateMonitor 的 `proctime` 触发 `DataManager::transHisData`→`WtDataWriter::transHisData`，为各合约排历史任务，再由 `proc_loop` / `dump_kline` 写压缩历史 `.dsb`。短时间启动后就退出，不一定执行了盘后归档；“已写实时 `.dmb`”和“已生成可用历史 `.dsb`”是不同检查项。


## 4．Runner 怎样知道 UDP 或共享队列在哪里

**地址来自配置配对，不是自动探测。** 两个进程各自加载配置。

UDP 示例：

```yaml
# datahub/dtcfg.yaml
broadcaster:
  active: true
  sport: 13997
  broadcast:
  - host: 127.0.0.1
    port: 19001
    type: 2

# run/tdparsers.yaml
parsers:
- active: true
  id: middle_udp
  module: ParserUDP
  host: 127.0.0.1
  sport: 13997
  bport: 19001
  code: SHFE.rb2701
```

`type: 2` 是 WT 原生二进制数据包。中台 `broadcast.port` 必须等于 ParserUDP 的 `bport`；中台 `sport` 必须等于 ParserUDP 的 `sport`。原例中把订阅端口叫 `bport` 是历史命名问题，UDPCaster 兼容这一旧字段，新的解释应按实际职责区分。

**13997 的“订阅”不是建立长期服务器推送关系。** `UDPCaster::do_receive` 收到订阅/快照请求后，查询当前 Tick 并回包；后续持续行情来自中台配置好的 broadcast / multicast 发送列表。ParserUDP 在自己的接收端根据订阅集合过滤合约，再把包转成 WT Tick。UDP 不提供逐条确认、重传和可靠历史补齐。

共享映射文件示例：

```yaml
# datahub/dtcfg.yaml
shmcaster:
  active: true
  path: ../ipc/ticks.queue

# Runner 的 parser 配置；这个方案替代 UDP parser
parsers:
- active: true
  id: middle_shm
  module: ParserShm
  path: ../ipc/ticks.queue
  code: SHFE.rb2701
  checkspan: 100
```

双方必须打开同一个文件。运行在不同容器时需要把相同宿主文件挂载给双方；即使字面路径一样，也必须确认指向同一挂载，不存在跨机器的 mmap 共享。

ShmCaster 创建并重置一个 8192 项的环形队列，写一项后发布可读索引；ParserShm 建立映射，轮询可读索引并逐项读取。这里的传输队列与 `FUT_Data/rt/*.dmb` 行情存储是两个不同映射用途。

```cpp
// src/WtDtCore/ShmCaster.cpp:51，真实核心写法
uint64_t wIdx = _queue->_writable++;
uint64_t realIdx = wIdx % _queue->_capacity;
_queue->_items[realIdx]._type = 0;
memcpy(&_queue->_items[realIdx]._tick,
       &curTick->getTickStruct(), sizeof(WTSTickStruct));
_queue->_readable = wIdx;
```

它是一种无互斥锁的环形传输实现；当前索引声明是 `volatile uint64_t`，未见严格 release/acquire 原子发布协议、消费者追不上时的可靠补包或背压。**因此不能把“无锁”推广成任意平台、任意负载下已证明的数据可靠性保证。** 本次尚未验证 SHM 传输；UDP 链路是否通过也必须以 Runner 实收和策略事件为证据。


## 5．从策略信号到柜台订单：逐层负责什么

收到 UDP / SHM Tick 后，`WtCore::ParserAdapter::handleQuote` 校验日期、查合约、过滤订阅，并把原始代码 `SHFE.rb2701` 转为策略标准代码 `SHFE.rb.2701`；`WtCtaEngine::handle_push_quote` 交给 `WtCtaRtTicker`。时钟推进行情事件与分钟结束，由 Reader 更新 K 线闭合，再触发相应策略调度。

### CTA 的理论仓位和柜台仓位是两本账

`stra_set_position(code, 1)` 表示策略目标为净多 1 手，不是立即成功报一个买单，更不是成交确认。源码 `CtaStraBaseCtx::stra_set_position` 先 `append_signal`；下一 Tick / 相应调度时，上下文以理论价格更新理论持仓和理论盈亏。分钟调度会汇总各策略目标；Bar 内或条件触发则可能立即提交仓位变化量。

组合再把目标交给执行器，执行器查 TraderAdapter 的真实持仓、未完成量与通道 ready 状态，计算差额。**策略的 `trades.csv` 可以已经有理论成交，而柜台订单仍未成交、被拒绝或未发出。** 真正的柜台成交通知与理论 CTA 记账必须对账。

核心链路：

```text
CTA 策略 → stra_set_position
→ CtaStraBaseCtx::append_signal
→ on_tick / on_schedule → do_set_position（策略理论账）
→ WtCtaEngine::on_schedule 或 handle_pos_change
→ 策略过滤、合约过滤、主力映射、组合风控系数
→ WtExecuterMgr::commit_cached_targets / handle_pos_change
→ 根据 routers 选择执行器
→ WtLocalExecuter::set_position / on_position_changed
→ 执行器 scale、目标归并、执行单元、通道流控
→ WtMinImpactExeUnit::set_position / do_calc
→ 查实际持仓、未完成单，选价格、拆数量、下单间隔
→ WtLocalExecuter::buy / sell
→ TraderAdapter::buy / sell
→ 开平规则、可用多空/今昨仓、合约数量上限、交易时段
→ openLong / closeShort / ... → doEntrust
→ ITraderApi::orderInsert
```

`WtMinImpactExeUnit` 管理单笔数量、最新 Tick 要求、对手价/己方价/最新价、偏移跳数、涨跌停价裁剪、超时撤单和重算，不负责生成盈利信号。它会等反向未完成单撤掉，避免同时累积相反方向订单。

启用 `strict_sync` 时，执行器还可能把未纳入目标管理的柜台持仓清零。新实验连接已有账号时，不应把该选项当成普通初始化开关，否则会触发实际平仓意图。

### 风控有不同层，不是一份配置全包

| 层 | 核心位置 | 作用 |
|---|---|---|
| 策略 | 自己的 CTA / Python 代码 | 信号、仓位上限、止损、最大交易次数、交易前的资金预算 |
| 过滤器 | `WtFilterMgr`，`env.filters` | 按策略、合约、执行器停用或覆盖目标；支持运行中重读 |
| 组合风控 | `WtRiskMonFact.WtSimpleRiskMon`，`env.riskmon` | 日内或多日回撤后缩放组合目标；基于 WT 理论权益 |
| 执行器 | `WtMinImpactExeUnit` | 拆单、定价、节奏、超时撤单、未完成量控制 |
| 交易通道 | `TraderAdapter`，trader 的 `riskmon` | 下单/撤单时间窗口、累计限额、自成交状态等 |
| 开平规则 | `ActionPolicyMgr`，`bspolicy` | 根据持仓和额度选择开仓、平今、平昨 |
| 柜台 / 交易所 | CTP / SimNow / 实盘柜台 | 可用资金、冻结保证金、交易权限、合法参数与交易所规则的最终校验 |

没有启用的风控对象不会自动保护账户。组合风控不是柜台保证金风控，也不能把 `base_amount` 当作向 CTP 账户注入现金。

### TraderCTP 与 TraderMocker 的分岔

TraderCTP 在通道准备好后，把 WT 委托转成 `CThostFtdcInputOrderField`：账户、交易所、合约、方向、开平、价格、数量、GFD/FAK/FOK 等，调用 `ReqOrderInsert`。因此如果通道指向 SimNow，启用真实执行器并产生目标差额，**会向 SimNow 发送订单**；是否 Python 写策略不改变这个事实。

TraderMocker 在本进程中接收相同委托接口，维护等待订单；它**还需要自己接到匹配行情**，使用 `udp_port` 接中台广播，不能仅靠 Runner 的 ParserUDP 自动供行情。撮合线程检查限价是否达到卖一/买一（`newpx` 可改用最新价），按对手量和剩余量拆分成交，更新本地订单与持仓，再发回模拟订单/成交回报。

当前 TraderMocker 不是交易所订单簿仿真：不完整模拟真实排队、隐藏流动性与资金保证金冻结；`queryAccount()` 返回全 0 的 CNY 资金占位信息。它主要用于流程验证。持仓由 `mocker_N/positions.json` 恢复，近期修复使停止前等待线程结束再保存最终检查点。


## 6．柜台订单 / 成交回报如何回到执行器与文件

TraderAdapter 的初始化查询链：

```text
TraderCTP 连接、认证、登录、结算确认
→ TraderAdapter::onLoginResult
→ queryPositions → onRspPosition
→ queryOrders → onRspOrders
→ queryTrades → onRspTrades
→ queryAccount → onRspAccount
→ _ready=true → 通知各 sink：on_channel_ready
```

订单和成交推送是另一条异步链：

```text
CTP OnRtnOrder
→ TraderCTP::makeOrderInfo
→ TraderAdapter::onPushOrder
→ 识别 localid/userTag、更新订单/剩余量/冻结与统计
→ orders.csv（savedata=true）
→ WtLocalExecuter::on_order
→ 该合约执行单元 on_order → 订单监控/撤单后重算

CTP OnRtnTrade
→ TraderCTP::makeTradeInfo
→ TraderAdapter::onPushTrade
→ 更新实际多空今昨持仓、未完成量、自成交检查
→ trades.csv、rtdata.json；请求最新资金
→ WtLocalExecuter::on_trade
→ 对应执行单元 on_trade
```

报单错误走 `OnRspOrderInsert` / `OnErrRtnOrderInsert`→`onRspEntrust` 或错误回调→执行器 `on_entrust`；撤单请求走 `TraderAdapter::cancel`→`orderAction`→CTP 回报。一次 `ReqOrderInsert` 返回 0，只说明请求进入 API，并不代表柜台接受或订单成交。

账户查询不只发生在登录时。`WtCtaEngine::on_schedule` 末尾会异步调用 `TraderAdapterMgr::refresh_funds()`，逐通道 `queryFund()`→`queryAccount()`；`onPushTrade` 每次成交后也会请求最新账户。`queryFund` 只在通道完全 ready 时查询，因此策略可以读取保存的 CNY 快照并校验更新时间，但不能保证休市、无正常调度或连接失效时仍按固定周期刷新。本版本未发现单独可配置的账户查询周期。

核心回调代码：

```cpp
// src/TraderCTP/TraderCTP.cpp:1035，摘录
void TraderCTP::OnRtnOrder(CThostFtdcOrderField *pOrder)
{
    WTSOrderInfo *orderInfo = makeOrderInfo(pOrder);
    if (orderInfo) {
        if (m_sink) m_sink->onPushOrder(orderInfo);
        orderInfo->release();
    }
}
// OnRtnTrade 同样转换后调用 m_sink->onPushTrade(tRecord)
```

```cpp
// VM src/WtCore/TraderAdapter.cpp:2129、2247，摘录
for (auto sink : _sinks)
    sink->on_order(localid, stdCode.c_str(), isBuy,
                   orderInfo->getVolume(), orderInfo->getVolLeft(),
                   orderInfo->getPrice(), orderInfo->getOrderState()==WOS_Canceled);
for (auto sink : _sinks)
    sink->on_trade(localid, stdCode.c_str(), isBuy, vol, tradeRecord->getPrice());
```

`_sinks` 在 CTA 场景通常是执行器。CTA 理论成交记录与真实柜台回报分开；BaseCtaStrategy 没有 `on_order/on_trade` 钩子；需要直接处理订单回报时应理解 HFT 上下文与通道接口，不能给 BaseCtaStrategy 虚构柜台成交钩子。

当前默认生成目录见 `src/WtCore/WtHelper.cpp`：

```text
run/generated/
├─ marker.json                  引擎、策略、执行器、通道清单
├─ stradata/<策略ID>.json        策略理论持仓、信号、条件等
├─ userdata/ud_<策略ID>.json     策略自定义键值状态
├─ execdata/...                 执行器检查点
├─ portfolio/datas.json         组合理论持仓与权益
├─ portfolio/trades.csv         组合理论成交
├─ portfolio/closes.csv         组合理论平仓统计
├─ portfolio/funds.csv          组合理论资金曲线
├─ outputs/<策略ID>/            策略 trades/closes/funds/signals/positions 等
└─ traders/<通道ID>/
   ├─ orders.csv                实际柜台委托及状态
   ├─ trades.csv                实际柜台成交
   └─ rtdata.json               实际通道资金与持仓快照
```

理论状态、执行器状态、柜台快照与行情文件分层保存，是因为它们解决不同问题。重新启动时策略加载自己的检查点，通道还会重新查询柜台；一份 `rtdata.json` 不能替代实际账户对账，监控数据库中的用户也不是持仓恢复来源。


## 7．Python CTA 与 C++ CTA 的共同部分

wtpy 不需要再启动 C++ `WtRunner` 可执行文件来运行同一策略。Python 入口创建 `WtEngine`，包装器加载 `WtPorter` 动态库；WtPorter 的运行器承担类似 C++ WtRunner 的配置和模块组织工作。Python 策略对象通过 ctypes 回调连接 `ExpCtaContext`。

从行情到执行器、TraderAdapter、TraderCTP / TraderMocker 的后半段仍是 C++。Python 改变的是“策略对象由谁创建、策略事件跨哪一层回调”，不是增加第二套撮合或交易通道。Python CTA 仍使用目标仓位语义，仍需要 parser、Reader、executer、trader、action policy 与风控配置。

推荐 Python 运行层保留 `run/run.py`、`run/strategies/`、配置和生成状态；安装好的 `wtpy` 包及 `wtpy/wrapper` 内 C++ 动态库是运行依赖。库加载时既可能搜索工作目录插件，也可能回退包装库目录；应使用确认兼容的一套编译产物，避免 Python 包自带旧核心库与新插件混用。具体 ctypes 回调与启动顺序由配套 Python 文档展开。
