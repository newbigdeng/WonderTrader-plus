# SimNow 接入：先把行情和查询接通，再验证交易

本地 TraderMocker 使用人工报价撮合，SimNow 由 CTP 行情和交易接口连接远端服务。替换接口之后，登录、合约、会话、行情、账户和订单都要逐层验收。

## 1. 三个程序分别干什么

CTPLoader 查询合约和品种，完成后退出。QuoteFactory 通过 ParserCTP 接收行情，再做存储和 UDP 广播。WtRunner 加载 TraderCTP 处理交易会话；接通 Runner 的行情 parser、策略与执行器以后，才组成完整策略链路。

```text
CTPLoader → 合约/品种文件 → 中台和 Runner 识别合约
CTP 行情 → QuoteFactory → 存储 + UDP → Runner → 策略/执行器
CTP 交易 ←→ TraderCTP ←→ TraderAdapter ←→ 执行器
```

无交易测试故意将 Runner 的策略、执行器及行情 parser 留空，只验证交易登录和查询。此时交易通道 ready 不表示 UDP→策略链路已经验收。

## 2. 先检查运行副本与插件

使用独立运行副本，基础数据、日志、CTP flow 和持仓文件各自隔离。新环境只复制程序、必要插件与确认过的基础数据，不复制旧环境的订单和会话状态。

SDK 从旧接口升级到 v6.7.13_20260225 后，创建 API 的函数多了生产模式参数，C++ 符号随之变化。隔离适配重新编译 ParserCTP、TraderCTP 和 CTPLoader，确保头文件、链接库和运行库成套使用。

部署又遇到原生库路径问题：WT 插件按约定名字加载 CTP 库，不能随意加 `lib` 前缀。实际运行布局中的名字为：

```text
datahub/parsers/thostmduserapi_se.so
run/traders/thosttraderapi_se.so
loader/thosttraderapi_se.so
```

这些改动解决的是 ABI 和部署装配。它们位于隔离适配副本，源码正式合并情况与本地运行验收分开记录。

## 3. 查询基础数据，再检查会话映射

在本地私密配置填写账户和凭据，分别选择对应环境的行情、交易前置及 SDK 生产模式。凭据、flow 和账户文件不上传仓库。

先运行 Loader，逐层观察连接、认证、登录、查询完成。查询输出另存新目录，检查合约数量、目标合约及品种定义后再决定更新 common。

实际成功查询得到 852 个合约、87 个品种，包含 rb2701。但新增品种与本地 session 模板未完全匹配，仍有 19 个缺口；合约查询成功不自动补齐会话规则。缺少 session 导致品种或合约被跳过，应修基础数据映射后再验证。

## 4. 第一阶段只测行情

启用中台的 CTP parser，并只订阅少量目标合约。先检查加载数量与 active 配置，再看连接、登录、订阅成功，最后核对连续 Tick、时间戳、交易日及行情落盘。

曾出现默认配置加载 0 个 parser。根因是配置未启用，程序不会发起行情连接；切到专用已启用配置后变成 1 个 parser。这是配置修正，不是 CTP 源码修复。

FUT_Data 出现 `cache.dmb` 只能说明缓存初始化；要用实际 Tick 或逐条数据确认收到了行情。本地 holiday 日志来自状态机，也不能代替远端服务状态证据。

## 5. 第二阶段测交易登录与只读查询

保持策略和执行器关闭，依次看到登录、通道初始化、持仓更新和 ready。随后将资金、持仓、未完订单与官方终端人工核对。自动生成 CNY 快照、持仓数组为空，只能说明本次查询返回的内容；账户一致性还要完成对账。

登录后正确停止，检查相关线程完成和进程退出。有限的正常关闭通过之后，仍需分别测试断网、持仓恢复和异常停止。

## 6. 已经测到的结果

| 时间/环境 | 现象 | 判断 |
|---|---|---|
| 10 月 9 日 Loader | 认证、登录、全量查询成功，852/87 | 查询链路通过 |
| 10 月 10 日早期启动记录 | Loader 连接后认证错误 7；中台默认 0 parser | 认证失败与配置未启用是两个问题，分别排查 |
| 10 月 10 日中午第一套 30001/30011 | TCP 拒绝；测试配置已加载 1 parser、1 trader，但无登录/查询/Tick | 建连失败，未到认证；具体远端或网络原因待验证 |
| 12:46–12:48 第二套 40001/40011 | Loader、行情登录订阅、交易查询与 ready 成功；登录后 INT 返回 0 | 接口登录、查询和有限正常停止通过 |
| 同次第二套 120 秒观察 | 无 Tick CSV；服务交易日为 20261008 | 持续行情未验收；未区分远端无推送与本地过滤的全部影响 |
| 17:04 第一套 30001/30011 | 再次拒绝连接，无查询或 Tick | 原阻塞仍在 |
| 17:10 第一套换 30003/30013 | 两端口仍拒绝；配置切换完成 | 新地址也未接通；原失败记录保留 |

限时 Loader 的 130 来自主动作 INT 停止；中台和 Runner 在对应未连接测试中正常返回 0。停止成功说明进程能结束，不能说明连接成功。所有这些轮次均未下单。

第二套在给定服务窗口之外仍响应过登录和查询，不能据此推断持续行情全天可用。第一套连接拒绝的根因也不能仅凭“周六”确定；复测时按当时服务公告、网络和日志重新判断。

## 7. 何时进入一手开平

持续行情有效、交易通道 ready、账户/持仓/未完订单对账一致后，才在独立配置中启用一个目标合约和最小策略。明确最大持仓、次数、开平方向及结束条件，检查订单、成交、撤单和最终持仓。

先完成空仓开平，再带仓停止并重启，确认没有因恢复重复开仓。最后验证跨交易日、断线重连与异常结束。第二套结算服务限制与结算确认 API 是否能返回，是不同问题：本次 ready 说明初始化未卡住，不代表跨日结算已验收。

虚拟机、容器的具体工作目录和已生成启动配置留在个人操作教程，仓库此处保留链路与验收过程。入口见 [主要链路](architecture.md)，当前缺陷见 [问题状态](issues-and-fixes.md)。
